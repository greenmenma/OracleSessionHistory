# できないこと・制約事項

## 不可能／完全にはできない機能

### 1. 取得間隔より短いセッションは記録できない
`gv$session` のポーリングでは、取得間隔（既定 5 秒）より短い時間で接続・切断したセッションは観測できません。接続アプリ表の回数は「観測できたセッション数」です。

**代替案**：すべての接続を確実に記録する必要がある場合は、Oracle の統合監査（`CREATE AUDIT POLICY ... ACTIONS LOGON`）またはログオントリガーで記録し、`unified_audit_trail` を取得する Provider を追加する方法があります（DB 側の設定変更が必要なため本システムでは未実装）。

### 2. 正確な切断時刻は分からない
切断時刻は「最後に存在を確認した時刻」で、実際の切断は「最後に確認した時刻〜検知した時刻」の間です。取得失敗が続いた後や Batch 停止後に検知した場合は「推定」と表示します。

### 3. DB Link の利用元は接続元 DB にアクセスできないと特定できない
監視対象側からは接続元 Oracle のサーバープロセスしか見えません。接続元 DB の接続文字列と参照権限が必要です。また：
- SQL 一致は、共有プールから SQL が追い出された後や、セッションが別の SQL を実行した後は検出できません。ビュー・プロシージャ内部で DB Link を使っている場合も SQL テキストには現れません。
- 接続元 DB 自体がさらに別の DB Link 経由で使われている（多段）場合、各段の DB を登録する必要があります。
- 接続元が Oracle 以外（SQL Server のリンクサーバー、Oracle Gateway 等）の場合は、プロセス一致の仕組みが使えません。

### 4. 切断された DB Link セッションの利用元
DB Link 利用元の取得は 30 秒間隔（既定）のため、短時間で終わった DB Link 利用は特定できないことがあります。間隔は設定画面で変更できます。

### 5. クライアントが偽装・未設定の情報
MACHINE・PROGRAM・OSUSER・MODULE はクライアントが申告する値です。アプリが設定していない、または接続プール（アプリサーバー経由）の場合、実際の利用者個人までは分かりません（アプリサーバーの端末・プログラムまで）。`CLIENT_IDENTIFIER` / `MODULE` / `ACTION` をアプリ側で設定してもらうと特定しやすくなります。

### 6. 接続アプリ（プロセス情報）が取れない場合
- 接続元が Windows 以外、DCOM で到達できない、アカウントの権限が足りない場合は、プロセス情報を取得できず PROGRAM でアプリを表示します。
- 取得間隔（既定 10 秒）より短い時間で切断したセッションや、問い合わせ前にプロセスが終了した場合は取得できません。過去の履歴（この機能の導入前）も取得できません。
- 接続プールを使うアプリは、プールを持つプロセス（w3wp.exe 等）までしか分かりません。
- `gv$session.process` に正しい PID を入れないドライバ（JDBC Thin の既定値など）は、別プロセスと判断して紐付けないことがあります。

### 7. 監査証跡（端末のログオン数）
- 監査証跡（DBA_AUDIT_SESSION）にはプログラム名が無いため、監査の件数はアプリ別には分けられません（端末の行のみ。下の段はこのシステムが取得したセッション数のため、端末の行の件数と合わないことがあります）。
- 標準監査でログオンを監査していない場合や、統合監査のみの環境では端末の行の件数が 0 になります。監査証跡を削除・アーカイブしている期間も件数が 0 になります。
- 監査の件数は `Collector:AuditLogonMinutes`（既定 10 分）ごとに取り直すため、「本日」の端末の件数は最大でその間隔だけ遅れます。
- 監査証跡の USERHOST とこのシステムの MACHINE は、表記（大文字小文字は区別しない）が同じ場合に同じ端末として扱います。

### 8. 実行ユーザの表示名
- AD に無いアカウント（ローカルアカウント・Unix のユーザ等）や、displayName が空のアカウントは、アカウントのまま表示します。
- 表示名は 1 日ごとに取り直すため、AD で名前を変えてから画面に反映されるまで最大 1 日かかります。
- 信頼関係の無い別のフォレストのドメインのアカウントは、Batch の実行アカウントで検索できないため表示名が出ません。

### 9. AQ スレーブ（Qnnn）の処理内容
どのキューを処理しているかを `gv$session` から安定して取得する方法がないため、種別の表示のみです。

## 運用上の制約

- 履歴 DB は SQLite（既定）または SQL Server です（`AppDb:Provider`、[setup.md](setup.md) 参照）。SQLite の場合、Batch と Server は同じマシン（または確実に共有できるローカルディスク）に置いてください。ネットワークドライブ上の SQLite は推奨されません。別マシン構成や大規模な運用では SQL Server を使ってください。
- SQLite と SQL Server の間でデータを移行する機能はありません。
- 画面に認証はありません。
- Oracle 側の時刻（`logon_time`）とアプリサーバーの時刻（`FirstSeenAt` 等）は別の時計です。タイムゾーンが異なる環境では表示がずれます。
